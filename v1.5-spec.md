## #4 — Consumer reports on the hourly chart + our own baseline

**Problem today.** Consumer crowd reports move the live busy % and the ranking,
but the hourly bar chart is still the static BestTime baseline. Reports feel
like they vanish, and the chart never reflects "it's slammed right now."

Two layers, ship the first now and the second when data volume allows.

### 4a — "% vs typical" overlay + reported-hour marker (near-term)
- **Frontend (S–M):** on the venue page, show a one-line delta above the chart —
  e.g. *"~15% busier than usual right now"* — and draw the current hour's
  consumer-reported level as a distinct mark on the bar chart (different fill +
  a small legend entry so it reads as "reported," not baseline).
- **Backend (S):** the venue-detail endpoint should return, for the current
  hour: the BestTime baseline value, the live busy_score, and their delta %.
  Baseline lives in the typical-hours data; live score is already computed. Just
  needs to be surfaced together so the frontend isn't re-deriving it.
- **Decision:** wording of the delta ("busier than usual" vs "X% higher than
  normal") — pick one label and keep it consistent with the ranking copy.

### 4b — Roam's own crowd-sourced baseline (the moat, longer-term)
- **Backend (M, but gated on volume):** `busy_score_history` already stores the
  time-series. Add a rollup that computes, per venue × weekday × hour, a median
  from accumulated reports. Once a venue crosses a report threshold (e.g. ≥ N
  reports in a slot), **blend** our median with BestTime, then **replace** it
  entirely as confidence grows. Store the blended curve so the chart can read
  from one place.
- **Why phased:** this is chicken-and-egg with the density problem — needs
  report volume first. Keep BestTime as the cold-start baseline; flip per-venue
  as our data fills in. This is the asset no competitor has.
- **Decision:** the threshold N and the blend curve (linear ramp vs step). Start
  conservative; tune once real report volume exists.

## #5 — Filter deal/event tiles to the map viewport

**Goal.** Clicking the map centers on the user and shows only what's nearby;
tiles scroll in sync with the visible area instead of jumping across town.

- **Frontend (M):** in the split map/list view, on open center the map on the
  user's location; filter the deal/event tile list to the current map bounds;
  update the list on `moveend` (debounced ~300ms) so panning re-filters. Sort by
  distance from map center. Empty-state copy when the visible area has nothing.
- **Backend:** none — venues/deals already carry lat/lng; filtering is client-side
  against the current bounds.
- **Decision:** whether the list is strictly viewport-bounded or "viewport +
  nearest few" so it's never empty when zoomed in tight. Recommend the latter.

## #7a — Share deals + post to your story

**Goal.** Share a deal the way venues can be shared; optionally push it to your
own story.

### Share a deal (S–M)
- **Frontend:** share button on deal cards → native share sheet (Capacitor Share
  plugin) with a short blurb + a deep link to the venue/deal.
- **Backend:** reuse/extend the existing share route so a deal link resolves to
  the venue page with the deal highlighted. Confirm the deep-link route exists;
  add a `/share/deal/:id` resolver if not.

### Post a deal to your story (M)
- **Schema:** add an optional `deal_id` (FK → deals, ON DELETE SET NULL) to
  `stories` so a story can reference the deal it was created from. New column →
  no new table, but confirm RLS is already deny-all on `stories` (it is; service
  role unaffected).
- **Frontend:** "Post to story" action on a deal pre-fills the story composer
  with the deal (venue name, offer, image). Respects existing friends-only story
  visibility.
- **Decision:** does a deal-story expire with the deal, or stand alone once
  posted? Recommend stand-alone (snapshot the text at post time).

## #7b — In-app venue "sticker" on your Roam story (instead of Snapchat)

**Recommendation:** don't build a Snapchat integration. Roam can't create Snap
geofilters programmatically (those go through Snap's own paid per-location tool),
and the in-app Snap Camera Kit SDK is a heavy lift with unclear ROI at current
scale. Keep it in-house:

- **Frontend (M):** in the story composer, let users add a venue/Roam overlay
  ("sticker") to their photo — venue name + Roam mark, tasteful, a few presets.
  This is our own "geofilter," no third-party dependency, and it markets Roam on
  every shared story.
- **Backend:** none (overlay is client-side; the composited image is uploaded as
  the story image as today).
- **Later / marketing (not a build):** if we still want Snapchat presence, submit
  a couple of Roam-branded On-Demand geofilters for flagship Charlotte venues.
  Cheap experiment, handled in Snap's tool, no code.

## #8 — Custom venue map markers (paid tier)

**Goal.** Paid venues stand out on the map with their own logo pin. Strong
"why upgrade" perk — slot as a **post-launch premium feature**.

- **Schema (S):** `venues.marker_logo_url` (text, nullable) + a moderation flag
  (e.g. `marker_approved boolean default false`). New columns only.
- **Backend (M):** owner endpoint (claimed venue + plan in `pro`/`premium`) to
  set the logo; validate it's a real image + size cap; store URL. Only serve
  `marker_logo_url` in the venue list when the plan is paid **and** approved —
  gate on both so a lapsed plan reverts to the default pin. Reuse the SSRF URL
  guard if the logo is fetched/proxied.
- **Frontend (M):** Mapbox custom marker for qualifying venues — circular,
  bordered, size-constrained so one logo can't dominate the map; default pin
  otherwise.
- **Stripe:** tie visibility to the existing plan gating; on downgrade the marker
  falls back automatically (because serving is plan-gated server-side).
- **Decision:** moderation flow — manual approve (simplest, low volume now) vs
  auto-approve with report/removal. Recommend manual while volume is tiny.
